## 1. Регламент стабильности и работы агентов (Anti-Timeout Policy)

1. **ТЕСТИРОВАНИЕ (In-Memory Testing Only):**  
   - Все автотесты `qa_bot` выполняются исключительно через `TestClient` (`starlette.testclient` / `httpx`) в оперативной памяти.  
   - **Прямые сетевые HTTP-запросы к localhost:8000 в тестах КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ.**

2. **БАШ-КОМАНДЫ (Single Command Execution):**  
   - Выполнять команды статического анализа и тестов строго по отдельности отдельными вызовами.  
   - **Категорически запрещено объединять `pytest`, `flake8`, `mypy` в один bash-вызов через `&&`.**

3. **РАБОТА С ФАЙЛАМИ (Terminal-Driven File Operations):**  
   - Создание и модификацию файлов производить через терминал или проверенные файловые операции без зависаний.

4. **ВЕДЕНИЕ ЖУРНАЛА (Continuous 9-Agent WORKLOG Protocol):**  
   - **Каждая без исключения выполненная задача, рефакторинг или UI/Backend изменение ОБЯЗАТЕЛЬНО фиксируется в `WORKLOG.md` синхронно с коммитом.**  
   - **В каждой записи обязательно подробно расписывается вклад всех 9 ролей команды из `AGENTS.md` (`pm_bot`, `py_bot`, `ui_bot`, `qa_bot`, `devops_bot`, `design_bot`, `seo_bot`, `load_bot`, `ai_bot`).**  
   - **Ни одна задача не считается выполненной без синхронной записи в `WORKLOG.md`.**

## 2. Технологический Enterprise-стек (Tech Stack)

### 🖥️ Серверный уровень (Backend & Storage):
- **Среда выполнения:** Python 3.12 (Strict MyPy Type Annotations, Asyncio).
- **Веб-фреймворк:** FastAPI 0.115+ / Starlette ASGI.
- **ASGI-сервер:** Uvicorn с пулом воркеров и оптимизацией keep-alive соединений.
- **Основная СУБД:** PostgreSQL 16+ (транзакционность, аудит смарт-контрактов, сессионные данные) через `asyncpg` и `SQLAlchemy 2.0`.
- **In-Memory хранилище и очереди:** Redis 7+ (кэширование ответов LLM, распределенные локи, очереди задач SAQ/Celery).
- **Валидация:** Pydantic v2 (строгие DTO-модели для всех контрактов и API).

### 🤖 Интеграция ИИ (AI Engine & Circuit Breaker):
- **Основной провайдер:** Google Gemini REST API (`v1beta/models/gemini-flash-latest`) в режиме Structured JSON.
- **Отказоустойчивость (Circuit Breaker):**
  - Реализация на базе `pybreaker` / `tenacity` с тремя состояниями (*Closed*, *Open*, *Half-Open*).
  - Порог сбоев: 3 подряд таймаута / ошибки 503/429 переключают контур в *Open* на 30 секунд.
- **Детерминированный (Deterministic) Fallback:**
  - При недоступности облачной LLM система мгновенно переключается на локальный детерминированный семантический процессор.
  - Нулевая вероятность отказа или зависания интерфейса для пользователя.

### 🎨 Клиентский уровень (Frontend Build):
- **Сборщик:** Vite (мгновенный HMR, оптимизированный бандлинг).
- **Стилизация:** PostCSS + Tailwind CSS v3 (адаптивная сетка, дизайн-токены, обсидиановая тема Helias).
- **Интерактивные виджеты:** Vanilla JavaScript ES6+ (без тяжелых runtime-зависимостей).
- **Шаблонизация:** Jinja2 с поддержкой i18n (RU / EN) и сохранением контекста в защищенных Cookie.

### 📊 Наблюдаемость и мониторинг (Observability):
- **Отслеживание ошибок:** Sentry SDK (runtime-ошибки бэкенда, необработанные JS-исключения, контекст сессий).
- **Метрики и телеметрия:** Prometheus client + Grafana (RPS, латентность Uvicorn p50/p95/p99, время ответа LLM, кэш-хиты Redis).
- **Аудит безопасности:** Логирование в формате JSON с маскированием персональных данных.

## 3. Релизный протокол и ветвление (Staging Gate Protocol)

### 🌿 Структура веток:
```
feature/* -> dev -> staging -> main
```
> ⛔ **КРИТИЧЕСКОЕ ПРАВИЛО:** Прямой коммит и прямой автоматический мердж в ветку `main` **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ**.

### 🚦 Staging Gate Protocol (Правила допуска в Production):
Мердж ветки `staging` в `main` и деплой на Production разрешены **ТОЛЬКО** при одновременном выполнении условий:
1. Автоматический прогон Unit & API тестов в памяти через `TestClient` (100% критических путей пройдено, 0 ошибок).
2. Сквозные E2E-тесты интерфейса (Playwright сценарии).
3. Нагрузочные испытания (k6 run, p95 latency < 350ms).
4. AppSec / SAST сканирование (Trivy / Bandit).
5. Ручной допуск (Gatekeeper Approval от `pm_bot`).

Для исключения таймаутов, падений и бесконечных запросов на ручное подтверждение (Edit/Create Approval) при делегировании задач субагентам:

1. **ОПЕРАЦИИ ЧЕРЕЗ ТЕРМИНАЛ**:
   Требовать от субагентов (py_bot, ui_bot, qa_bot, devops_bot, designer_bot, seo_bot) при массовом создании и правке файлов отдавать приоритет исполнению команд через консоль/терминал (Bash/Shell: cat, echo, sed, git, python-скрипты), если создание/правка через UI вызывает диалоги подтверждения.

2. **РЕЖИМ ALWAYS ALLOW**:
   Если операция требует работы напрямую через инструмент Edit/Create, субагент должен генерировать правки так, чтобы они подпадали под разрешенные правила окружения (Always Allow), либо завершать операцию атомарно без зависания в ожидании интерактивного ввода.

3. **АТОМАРНОСТЬ И ТАЙМАУТЫ**:
   Декомпозировать задачи для субагентов на маленькие итерации, чтобы каждый субагент успевал выполнить команду и вернуть статус выполнения до наступления Agent Execution Timeout.
